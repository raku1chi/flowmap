# Jev を使った判定の試験

> **2026-09-26 の判断**: Jev は画面の同定（合流・データ区間）には使わず、危険な操作の判定だけを任意の補助として残した。
> 「同じ画面を何度も辿る」の主因は探索エンジン側（再現に前の試行の localStorage が持ち越される、押していないフォームを埋める）にあり、
> 決定的に直せたため。理由の詳細は DESIGN.md §5「Jev による判定（任意・実験的）」。以下はその前の試験の記録。

flowmap の機械的な判定のうち、意味の分かる判定が効きそうな 3 か所で、[Jev](https://docs.typesafe.ai/introduction)（TypeSafe の型付き判定モデル）を試した。この結果をもとに `src/jev.ts` として本体に組み込み、`--jev` で使えるようにした（DESIGN.md §5）。ここの試験は、問いや閾値を変えたときに採点し直すために残している。問いは本体の `src/jev.ts` のものをそのまま使う。

| 問い | flowmap の中の対応箇所 | 現行の機械的ルール |
| --- | --- | --- |
| links: 同じ形の兄弟リンク群は「同じ作りの画面を別データについて開く」ものか | データ区間の自動学習（§5） | 1 区間だけ違うリンクが 3 本以上あれば学習 |
| pages: 2 つの画面は同じ画面か（データは違ってもよい） | 分かれたノードの合流 | シグネチャの一致 |
| actions: その操作はサーバーのデータを変えるか | 押さない操作の除外（§7） | `denyText` の部分一致 |

## 使い方

```sh
cp .env.example .env                              # TYPESAFE_API_KEY を入れる（.env は git 管理外）
pnpm exec tsx experiments/jev/capture.ts          # 8787 とデモ 3210 を開いて正解付きのケースを作る（キー不要）
pnpm exec tsx experiments/jev/ask.ts              # 全ケースを Jev に聞き、現行ルールと並べて採点する
pnpm exec tsx experiments/jev/review.ts flowmap-out/runs/<dir>   # 探索結果の画面を合流させたらいくつになるか
```

出力は `flowmap-out/jev/` に出る（dataset.json、results-*.json、report-*.md、review-*.md）。API キーはどこにも書き出さない。

| ファイル | 役割 |
| --- | --- |
| cases.ts | 正解ラベル付きのケース定義。8787 とデモの実画面から取るものと、機械的ルールの苦手な形を試す架空のもの |
| page.ts | 画面を撮って Jev に渡す要約と差分を作る。探索エンジンと同じ手順で経路を再生する |
| jev.ts | HTTP API のクライアントと問いの定義 |
| capture.ts / ask.ts / review.ts | 上の 3 つのコマンド |

## 結果（2026-09-25、jev-1.13.0、閾値 0.5、2 回実行）

| 問い | 件数 | 現行ルール | Jev（日本語の問い） | Jev（英語の問い） |
| --- | --- | --- | --- | --- |
| links | 16 | 12 | 15〜16 | 16 |
| pages | 21 | 16 | 21（2 つの問いに分けた版） | 19 |
| actions（日本語のラベル） | 40 | 23 | 39 | 40 |
| actions（英語のラベル） | 16 | 8 | 15 | 16 |

- **現行ルールの誤りを Jev はほぼ全部拾った。** links では設定・管理画面・マイページの各セクションを誤って合流させる形と、先頭区間のユーザー名（`/hanako`）を取りこぼす形の両方。actions では「出荷する」「承認する」「送金する」など `denyText` に無い操作 17 件と、英語の「Log out」（`logout` と綴りが違う）。
- **日本語でも実用になった。** 公式には英語が主だが、日本語のラベルと画面で英語の問いと同程度だった。pages だけは日本語の問いのほうが明確に良かった（画面の中身が日本語のため）。
- **実際の探索結果（8787、22 画面）をレビューすると 10 画面になった。** 企業一覧の絞り込み・ページ違い 6 画面、企業詳細 3 画面、ランキング 3 画面などが合流し、ヘッダのメニューを開いた状態は別の画面のまま残った。
- **費用と速さは問題にならない。** 全 93 ケースを 1 回聞いて入力 7.6 万トークン（約 0.003 ドル）、応答は中央値 0.2 秒。

## 分かったこと

1. **問いは字義どおりに読まれる。** 初版の pages の問いを「同じ画面に**別の**データを表示したもの」と書いたら、違いのない 2 画面を「別のデータではない」として 0.24 と答えた。公式の jaggedness ページの 1 番目の失敗パターンそのもの。
2. **判断は分けてコードで組む。** pages は「種類と目的が同じ画面か」と「違いは UI 操作（タブ・メニュー・ダイアログ）によるものか」の 2 つに分け、合流の度合い = min(種類が同じ, 1 − UI 操作の違い) とした。違いのない組は Jev に聞かずコードで同じと決める。同じ実行で比べると、正例の最小値が 0.62 から 0.87 に上がり、負例の最大値が 0.46 から 0.34 に下がった。実探索のレビューで保留になる組は 46 組中 22 組から 5 組に減った。
3. **値は実行ごとに少し揺れる。** 同じ入力で最大 0.07 動き、0.5 付近の判定が入れ替わった（管理画面の links が 0.47 と 0.52）。0.5 で決めず、0.7 以上なら「はい」、0.3 以下なら「いいえ」、その間は保留にすると、2 回の実行とも誤った合流は 0 件だった。
4. **「編集」は迷う。** 開くだけで保存はしないが 0.4〜0.6 になる。安全側に倒して除外しても網羅が少し減るだけ。

## 組み込み（2026-09-26）

試験の結果をそのまま規則にし、組み込みの途中で見つかった誤判定には「コードで決められることはコードで決める」で対処した。ask.ts の「探索での判定」の行が、この規則での採点になる。

| 判定 | 探索での規則 | 試験での結果 |
| --- | --- | --- |
| 操作 | 日英の問いのどちらかが 0.5 以上なら押さない。リンクは 0.7 以上のときだけ。タブと開閉は聞かない | 危険な操作の見逃し 0。「編集」ボタンを 1 件だけ危険側に倒した |
| 画面 | 違いのない組はコードで同じとする。それ以外は min(種類が同じ, 1 − UI 操作) が 0.7 以上なら合流 | 21 件すべて正解。誤った合流 0 |
| データ区間 | 日英の問いがともに 0.7 以上なら学習、そうでなければ見送る | 16 件すべて正解 |

- **合流と学習は、保留なら行わない。** 0.3〜0.7 の保留は、合流を増やさない側（現行ルールで分かれたまま・学習しない）に倒す。画面を見落とす誤りのほうが、重複が残る誤りより重いため。
- **組み込みで足した例外。** デモで「危険な操作」という名前のタブを 0.58、ヘッダの「お問い合わせ」リンクを 0.53 で危険と判定した。タブと開閉は性質上データを変えないので聞かず、リンクは GET の遷移なので閾値を 0.7 に上げた。どちらも試験データの判定は変わらない。
- **答えはキャッシュする。** `(モデル, 問い, state)` のハッシュで `flowmap-out/jev-cache.json` に保存する。同じ画面には同じ答えを返し、値の揺れで実行間の比較（§10）が崩れないようにする。
- **実アプリでの効果（8787）。** Jev なしで 21 画面・570 秒だった探索が、Jev ありで 9 画面・218 秒になった。企業一覧とランキングはそれぞれ 7 つの変種が 1 画面にまとまり、メニューを開いた状態は別の画面のまま残った。このアプリで押さなかった操作は 0 件だった。

## 制限

- ケースはこの試験のために作った 93 件で、架空のものを含む。閾値もこのケースを見て決めたので、別のアプリでは測り直す必要がある。組み込みで足した 2 つの例外も、デモで見つかった誤判定に合わせたもの。
- 実アプリは 8787 の 1 つだけ。レビューで企業詳細 2 画面は探索時のリンクが一覧から消えていて、同じ形の別の企業ページで代用した。
- 問いの criteria の例はケースと重ならないようにしたが、概念の定義（ログイン状態、タブやダイアログ）はケースと重なっている。
